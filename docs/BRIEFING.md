## 一、项目是什么

**CodeAtlas —— 面向大型 C 工程的 AI 知识库。**

解决的问题：读一个十万行级的 C 仓库，grep 逐行找效率低；直接把代码交给大模型，
会遇到上下文不足、同名符号混淆、答案无法追溯。

做法：把代码**离线编译成可查询的事实图谱**（用 Clang AST，不是靠模型抽取），
在线用四路混合检索回答问题，每个结论带证据引用，证据不足时拒绝作答。

**技术定位（这句话很重要）**：
> 本质是 GraphRAG，但图不是 LLM 抽的，是编译器给的 —— 所以可验证、可复现。

## 二、技术栈

Python 3.11 · libclang · SQLite（FTS5 + 递归 CTE）· numpy · FastAPI · typer · pytest

测试 76 项。无需 API key / GPU / 下载模型即可完整运行。

## 四、六个核心设计

1. **事实与推断分离**：编译器能 resolve 的调用记 `certain`，函数指针/取地址/宏展开
   记 `candidate` 并标注原因。**candidate 不参与调用链、影响分析、检索上下文。**
   理由：影响分析一旦给出错误的回归范围，工具就失去信任。

2. **定长检索摘要头（≤200 token）**：把每个函数的调用上下文压成定长摘要，
   图多跳扩展时只取摘要头不取函数体。实测同样约 4.5k 预算下，
   函数体模式只装下 5 个扩展节点，摘要头模式装下 18 个。

3. **确定性程序管边界，模型只管表达**：节点/边/生命周期全由代码控制，
   LLM 只做自然语言摘要和经验抽取，输出必须过 JSON Schema 校验。

4. **人工审核硬闸门**：LLM 抽取的经验一律 `pending`，审核前在检索中完全不可见
   （不是靠上层过滤，是 `chunk.visible=0` 的行根本不进 FTS5 索引）。有测试保证。

5. **证据分级与拒答**：A（编译器事实）/ B（已审核经验）/ C（生成的 Wiki）/ D（不进上下文）。
   A/B 级为 0 时拒绝下结论，只给排查线索。

6. **增量解析**：指纹算的是**依赖闭包**（TU 内所有仓库内头文件内容 + 编译参数哈希），
   边与翻译单元用关联表建多对多关系，撤销时按引用计数回收。
   有测试保证增量结果与全量重建**逐边一致**。

## 五、四个真实修复的 bug（简历/面试的核心资产）

这些是最难伪造的部分，请优先保留。

1. **`semantic_parent` 误判**：libclang 里 `semantic_parent` 对表达式节点返回的是
   语义上下文而非语法父节点。用它判断"是否处于被调位置"，导致每个正常调用的函数名
   又被记一条 `address_taken`，candidate 从 8 条真值膨胀到 461 条噪声。

2. **孤儿边清理吃掉函数指针边**：`DELETE FROM edge WHERE dst NOT IN (SELECT id FROM node)`
   把 `fn_pointer` 边全删了 —— 它们指向局部变量和形参，而这些不在常规节点采集范围内。
   mbedtls 上 candidate 显示只有 5 条，看着"代码很干净"，其实是这一类整个是空的。
   **教训：一个号称"区分事实与推断"却把推断集悄悄清空的系统，比不做这个设计更危险。**

3. **边数膨胀 15 倍**：第一版把 `tu` 放进 `edge` 唯一键，lwIP 上确定边从 11,471
   变成 174,071。危险的不是存储，是**统计口径失真** —— 简历上的数字会变成假的。
   改成关联表 + 引用计数回收才对。

4. **伪装成小毛病的解析缺陷**：lwIP 显示"诊断错误 124"，TU 总数也是 124，
   每文件恰好 1 个。实际是 `stddef.h` 找不到，libclang 作为库调用时拿不到
   clang 驱动才知道的 resource-dir，整条标准库头链断了。
   症状迷惑性在于**不会让解析失败**，只是 certain 边被系统性少算。
   补上 builtin 头目录后错误 124→5，多认出 112 条确定边。
   **教训：一个"每个文件都有但只有一个"的错误，比"少数文件很多错误"更可疑。**

## 六、三个负面/零收益结论（请务必保留）

**这些是差异化最强的部分。** 能说出"我测了，没用，原因是 X"的候选人极少。

1. **符号精确召回增益为零**（64.4% → 64.4%，MRR 反而略降）。
   根因：FTS5 配了 `tokenize="unicode61 tokenchars '_'"`，
   BM25 本身已经能精确匹配整个标识符，符号通道是重复劳动。
   它真正的价值在同名符号消歧场景，这两个语料太干净测不出来。
   **这一行没有因为数字不好看而从消融表里删掉。**

2. **图扩展的收益存在循环论证嫌疑，主动做了分题型拆解**。
   自动生成题的 gold 取自 certain 边，而图扩展走的也是 certain 边。
   拆开看（cJSON）：间接影响(2跳) +31.5pt、影响面 +12.7pt、被调关系 +11.1pt
   —— 全是金标来自图的题型；而符号定位 +0.0pt、语义理解 +0.0pt，两类非循环题型增益为零。
   **正确表述是"图多跳扩展使结构性查询召回提升 11~31 个点"，
   不是"混合检索整体提升召回"。** 评测工具现在会自动输出这张表并标注循环性。

3. **重排第一版是负收益，经过两轮诊断才转正**。
   第一版一律重排，Recall 明显下降（前缀匹配给了正权重，
   把"同名符号混淆"又引了回来）。第二版改成负权重后 63.9%，仍低于基线，
   **此时停止调参**（继续调就是往评测集上过拟合）。
   第三版逐题诊断，发现变差的 11 题全是结构性查询，想通机制：
   > 问"改 X 会波及谁"，答案是调用图上距离远、**内容上和 X 完全不像**的函数。
   > 内容相似度在结构性查询上是错误的排序信号。

   所以正确解法不是调权重，是**按查询意图决定要不要重排**。完整流水线重跑后为 65.8% → 66.4%，
   MRR 0.449 → 0.460。
   （lwIP 上数字不变，是因为它 58 题里 46 题是结构性查询，按设计全部跳过 ——
   这反而验证了意图路由生效。）

## 七、事实边界（写简历时不能越过）

**是真的：**
- 76 项测试，`bash demo.sh` 一键复现全部数字
- 在 lwIP(135k 行) / mbedtls(87k 行) / cJSON 三个真实开源 C 项目上验证
- 上述四个 bug 是开发中真实遇到并修复的
- 上述三个负面结论是真实测量的

**不是真的 / 不能写：**
- ❌ 不是实习经历，没有公司、团队、mentor
- ❌ 不是基带项目。语料是 lwIP / mbedtls / cJSON
- ❌ 不是"独立开发/从零实现"，代码由 AI 辅助完成
- ❌ 没有真实用户使用验证
- ❌ 向量通道是 TF-IDF + SVD（本质是 1990 年代的 LSA），**不是**语义嵌入模型
- ❌ 重排是启发式线性加权，**不是** learning-to-rank，权重按先验拍的不是训的
- ❌ 没做指针分析（points-to），函数指针目标不解析、只隔离

**【待补】（尚未完成，不要写成已完成）：**
- LLM 生成路径从未打过真实 API（有 13 项 mock 测试兜底，但没跑过真模型）
- 分层文档目前是模板渲染 + 可选 LLM 润色。**在真跑过 LLM 之前，
  不要称之为"LLM-Wiki"，只能叫"分层文档生成"**
- 换真实嵌入模型重跑消融（语义理解题当前只有 15%）

## 八、已知局限（建议主动写进简历或面试）

- 增量粒度到翻译单元，宏定义变更的跨 TU 语义变化未精确追踪
- 评测集 58/59 题偏小，分六类后每类约 10 题，置信区间宽；只评检索未评生成质量
- `unresolved` 类 candidate 占比偏高（mbedtls 上 369/380），成因是条件编译宏，未细分
- 规模只验证到 13.5 万行，更大规模下递归 CTE 表现未测
- 单语言（C）、单用户、无权限、无审计
