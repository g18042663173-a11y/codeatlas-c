# CodeAtlas 与 LLM Wiki 的关系

核查日期：2026-09-05。

结论：参考了方法论，不是移植或依赖某个同名应用，也没有完整复现 LLM 自主管理知识的能力。

## 原始来源

[Karpathy 的原始 LLM Wiki idea file](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 提出一种持久知识组织模式：保留原始资料，将整理后的知识维护为互相链接的 Wiki，并用规则文件约束处理过程。它不是给定数据库、前后端和向量引擎的标准软件框架。

原文的三层是 **raw sources / wiki / schema**；主要操作为摄取、查询和维护检查。CodeAtlas 的 **文件 / 模块 / 仓库** 是 Wiki 内部的领域层级，不能当成原文三层的直接复刻。

[nashsu/llm_wiki](https://github.com/nashsu/llm_wiki) 是另一份具体桌面应用实现，其 README 说明基于上述模式并做了扩展。CodeAtlas 没有使用它的 Tauri/React 实现。早期本地设计稿已明确区分这两者；旧稿只用于追溯设计意图，不作为功能完成证据，也不纳入本次公开提交。

## CodeAtlas 实际采用了什么

- 把部分理解工作前置，产出持久的 Markdown 页面，而不是每次问答都从头组织。
- Wiki 保留来源链接；查询可以从页面回到源码核验。
- 人工策划经验，索引是派生物；通过质量、审核、失效和重建过程维护知识。

## C 工程场景下的改造

- 原始事实来自冻结源码、编译配置和 libclang，不以模型陈述替代编译器事实。
- 用 USR、构建/内容哈希、knowledge_set 固定引用版本，并隔离 certain 与 candidate。
- 使用规则生成工程 Wiki 骨架；模型只能组织已有事实，自由叙述不自动变成可信知识。
- 原始会话不进入检索；经验经过精确锚点、QA 与人工批准才能成为 B 级证据。
- 一次运行固定一个快照，版本变化触发失效；模型只有受限只读工具。

## 尚不能称为完整 LLM Wiki 的部分

当前 Wiki 仍偏结构化工程摘要。跨函数机制综合、跨主题冲突辨析、持续自动维护，并未作为已验证的成熟能力交付。模型自主创建/更新可信知识也被刻意限制。原始模式与本项目的治理边界不同，不宜按“复制了完整架构”介绍。

面试可说：

> 我参考了 LLM Wiki 把临时理解沉淀为持久知识的思路，但针对 C 工程重新设计了事实来源、版本和审核边界。编译器产出事实，Wiki 组织背景，模型负责受限规划，人负责发布经验。是否值得增加知识层，另外通过固定代码检索的知识层消融来验证；目前不拿架构相似性当作效果证据。

代码入口：`wiki/generator.py`（工程页面）、`snapshots.py`（固定版本）、`publication.py`（发布一致性）、`agent.py`（知识使用）。评测方法见 [合理性修订](EVALUATION-VALIDITY.md)。
