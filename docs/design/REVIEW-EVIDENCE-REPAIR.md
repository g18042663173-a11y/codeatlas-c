# 评分材料修订：修输入，不重写历史答案

本轮修复的是评分证据包，不是重新生成 Agent 答案。Luna 的510个原始答案、三个正式 run hash、题目和 gold 保持不变。旧 V4 报告继续保留，存在证据传递问题的汇总暂不用于效果结论。

## 为什么需要复评

- 知识复用包存在标签重映射和正文丢失：54个答案全部纳入复评，不按原分数挑选。
- Wiki 包的标签映射未变，但有134个答案的实际引用范围不能被旧评分包完整覆盖；另外9个 detach 机制答案需要一致的源码核验。合计143个 Wiki 答案。
- “范围未完整覆盖”不是“答案错误”的计数，补回正文也不等于证明答案正确。

## 证据与可见性的边界

1. 从原始 `wiki_section/code_read` 事件恢复的正文标记为 `original_tool_output`，保留事件哈希、截断状态和续读位置。
2. 从当时冻结快照读取的核验源码标记为 `reviewer_only_verification`。它只能核对引用和结论，不能据此声称被测 Agent 当时读过全部内容。
3. 快照、数据库元数据、源码清单和文件哈希必须一致；函数锚点必须精确匹配 USR、相对路径、完整定义范围和哈希。
4. 评分材料保留所有实际引用及固定 gold 依据。正文去重采用可还原引用；C 展示压缩保留字符串和 token 间隔，遇续行或特殊换行保留原文。超预算不得静默截断。
5. 无需重新评分的旧记录必须仍绑定旧实际请求、提示词、资格和评分来源，不声称它们使用了新证据视图。

## 有限执行

新增请求共用一个持久化800次上限，仍受原5000次全局账本约束；并发2。失败和结果未知均计入上限，不自动重发未知请求。78个新增开发试次后置。

首先独立复评54个知识复用答案。输入核验：244个实际引用正文均与冻结素材一致；包含两份完整评分矩阵的最大估算仲裁输入为7953token，低于8000上限。主评分模型为已有 V4B 资格的 Sol。独立代码审阅9.25分是启动路径质量检查，不是模型效果分数。

新报告只有在双审和必要仲裁完成后才替代当前效果入口。提升、持平、退化或证据不足都必须按实际结果报告；不修改旧答案、gold或审核身份来获得正向数字。

## 2026-09-08 授权续跑

用户明确允许：仅评分模型的完整输入上限提高到 16,000；被测 Agent 的 8,000 输入、1,200 输出和冻结答案不变。评分传输绕开通用截断器，超过完整输入上限时在预算预留和网络发送前失败。校准、双审和仲裁使用同一上限，实际超时固定 180 秒、自动重试为零；上限、超时、授权哈希和客户端实现都绑定新批次。

lwIP 的 72 个范围风险答案重新评分，144 个无输入修订的旧评分仍保留原请求来源。原 8k 阻断清单保留，新 16k 清单只改变获授权的评分上限，不改变题目、答案、gold 或证据正文。

用户也明确允许为知识复用的一条超时答案建立补审批次。授权只限旧批次对应的两条 `TimeoutError` 评分槽，按 batch/role/call_id/request_hash/result_hash 精确绑定；原 53 个终局评分及旧超时记录不覆盖。再次发生结果未知不得自动重发或扩展目标。

本轮请求上限仍为共享 800 次、全局 5,000 次。续跑前已使用 316 次；lwIP 最坏 228 次，加单答案补审最坏 15 次，仍在剩余额度内。预算与传输代码独立审查通过（8.875/10，为实现审查分数，非模型效果）。

补审授权清单还绑定 53 个原终局、全部原始请求及资格记录、目标两条未知调用、运行时代码哈希和 180 秒超时；同一个原批次只能建立一个授权补审。续跑只恢复未发出的工作，不重发完成、失败或未知请求。补审模块独立审查 9.0/10，22 项定向测试通过；最多新增 2 次独立评分、12 次仲裁资格和 1 次仲裁，共 15 次请求。

两类修订均通过本地全量 498 项 Python 测试及 8 项 UI 测试。测试结果用于工程检查，不计入模型理解正确率。

最终报告适配另补 13 项测试：精简报告的逐试次结果在哈希和复核完整性通过后转换为独立统计视图，原报告不变，仍使用原来的仓库内机制等权与两仓库等权公式。两份真实 V5 与账本原始报告的完整差值/区间/seed 结果相同（2 仓库、40 任务、35 机制）；篡改、未决或不完整配对不得合并。独立代码审查 9.125/10，无阻断项。
