## ADR-1 为什么用 Clang AST，而不是 tree-sitter / 正则 / ctags

**决策**：用 libclang 配合 `compile_commands.json` 解析。

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 正则 / grep | 拿不到语义。`foo(` 可能是调用、宏、函数指针类型声明、字符串里的文本，正则分不了 |
| ctags / cscope | 只有符号位置，没有调用关系的类型信息，也解析不了宏展开后的代码 |
| tree-sitter | 只做语法解析，**不做语义解析**。它能告诉你"这是一个函数调用表达式"，但告诉不了你"这个调用具体指向哪个声明"。C 里同名 static 函数、宏展开、条件编译一多就废了 |
| clangd LSP | 能力够，但要跑一个常驻进程做 IPC，批量离线解析十万行时开销和复杂度都比直接调 libclang 高 |

**核心理由**：这个项目的立身之本是"**事实必须可信**"。tree-sitter 给的是语法树，libclang 给的是**经过类型检查和宏展开的语义树**。只有后者能回答"这个 CallExpr 到底 resolve 到哪个 FUNCTION_DECL"，而这正是 certain 边的定义。

**代价（要主动承认）**：需要 `compile_commands.json`，对构建系统有依赖；解析速度比 tree-sitter 慢一个量级（mbedtls 65 个 TU 用了 11 秒）。

> **追问：那没有 compile_commands.json 的项目怎么办？**
> 做了三级降级：① 有编译数据库就用；② 没有但给了 `-I` 就目录扫描 + 手工 flags；③ 都没有就裸解析。
> 降级时会在 `meta` 表里标记 `degraded=1` 并在 CLI 上明确告警，**因为降级模式下宏和头文件解析不全，
> 产出的图谱质量下降，这件事必须让使用者知道**，不能悄悄降级假装没事。

> **追问：不完整编译能解析吗？**
> 能。libclang 是容错解析器，即使有诊断错误也会尽力产出 AST。所以只需要 `cmake configure` 成功
> 拿到 `compile_commands.json`，**不需要完整编译通过**。mbedtls 那次有 84 个诊断错误（缺
> tf-psa-crypto 子模块），照样抽出了 888 个函数和 4564 条确定边。但我在 stats 里把诊断错误数
> 打出来了，因为它是解析质量的直接指标。

## ADR-2 为什么把调用边分成 certain 和 candidate

**决策**：`edge.confidence ∈ {certain, candidate}`，candidate 不参与调用链、影响分析、检索上下文。

| reason | 判定条件 | 归类 |
|---|---|---|
| `ast` | CallExpr 能 resolve 到 FUNCTION_DECL | certain |
| `fn_pointer` | 通过 VAR_DECL / FIELD_DECL / PARM_DECL 调用 | candidate |
| `address_taken` | 函数名被引用但不在被调位置 | candidate |
| `unresolved` | 完全 resolve 不了（宏展开、声明缺失） | candidate |

**为什么不全都算调用边（最常见的追问）**

因为**影响分析的价值完全建立在准确性上**。如果我告诉你"改这个函数会影响这 35 个地方"，
而其中 10 个是函数指针猜出来的假阳性，你验证两次发现是错的之后，就再也不会用这个工具了。
一个会说谎的工具，比没有工具更糟 —— 它会让人基于错误信息做决策。

**为什么不干脆丢掉 candidate**

因为"这里有一个我确定不了的调用"本身是**高价值信息**。基带、驱动、协议栈这类代码里，
函数指针表（ops struct）是主要的多态手段，把它们全丢掉等于丢掉了架构的骨架。
所以我保留它们，但**放在单独的一栏，明确标注"需人工确认"**，让人自己判断。

**实测**：cJSON 上 candidate 占调用边 4.6%，mbedtls 上占 27.2%。
后者高是因为大量条件编译宏导致的 unresolved。这个比例本身就是代码风格的一个指标。

> ⚠️ **踩过的坑（这段一定要讲）**
>
> 我最初用 `cursor.semantic_parent` 判断一个 `DECL_REF_EXPR` 是不是处于"被调位置"。
> 但 libclang 里 `semantic_parent` 对**表达式节点**返回的是所在函数/TU 这样的**语义上下文**，
> 不是语法父节点。结果每个正常函数调用的函数名又被额外记了一条 `address_taken` candidate 边 ——
> candidate 从 8 条真值膨胀到 461 条噪声。改成显式父节点递归后才对。
>
> 更隐蔽的第二个坑：`persist()` 里有一句清理孤儿边的 SQL
> （`DELETE FROM edge WHERE dst NOT IN (SELECT id FROM node)`）。
> 函数指针边指向的是**局部变量和形参**，而我从没为局部变量建过节点 ——
> 于是全部 `fn_pointer` 边被静默删光。mbedtls 上 candidate 显示只有 5 条，
> 看起来"代码很干净"，实际上是这一类边整个是空的。
>
> **教训**：一个号称"区分事实与推断"却把推断集悄悄清空的系统，比不做这个设计更危险，
> 因为它给了你虚假的安全感。修复后我把孤儿清理改成显式报数，绝不静默。
> 现在有测试 `test_traversal_never_includes_candidate` 专门守这条不变量。

<a id="adr-3"></a>
## ADR-3 为什么用 SQLite 存图，而不是 Neo4j

**决策**：`node` / `edge` 两张表 + 递归 CTE 做多跳遍历。

```sql
WITH RECURSIVE reach(id, hop) AS (
    SELECT ?, 0
    UNION
    SELECT e.dst, r.hop + 1
      FROM edge e JOIN reach r ON e.src = r.id
     WHERE e.kind = ? AND e.confidence = 'certain' AND r.hop < ?
)
SELECT id, MIN(hop) FROM reach WHERE hop > 0 GROUP BY id
```

**为什么不用 Neo4j**

1. **规模不需要**。目标是单机十万级节点，递归 CTE 在这个量级毫秒级返回（实测 P50 12ms）。
   Neo4j 的优势在千万级以上和复杂图算法，这里用不上。
2. **部署成本**。Neo4j 要起服务、配内存、管版本。这个项目的定位是 `git clone && pip install` 就能跑，
   多一个外部服务就少一批愿意试的人。
3. **一致性**。图、全文索引（FTS5）、业务数据在**同一个事务**里。用 Neo4j 就变成跨库双写，
   要自己处理一致性，为了一个用不上的性能优势引入一类新 bug。

**怎么保证将来能换**：所有图遍历封装在 `graph/traverse.py` 一个文件里，
上层只调 `neighbors()` / `impact()` / `resolve_symbol()`。真到了要换的规模，只改这一个文件。

> **追问：递归 CTE 会不会爆炸？**
> 会，所以有 `max_hop` 硬截断（默认 2~3 跳），且用 `UNION`（不是 `UNION ALL`）自动去重防环。
> 另外只走 certain 边，本身就把边数砍掉一大截。

## ADR-4 为什么要做"检索摘要头"，而不是直接塞函数体

**决策**：每个函数额外生成一个**定长 ≤200 token** 的摘要头，图多跳扩展时只取摘要头。

摘要头内容：一句话职责 + 被调(≤12) + 调用者(≤8) + 关键头文件 + 关键类型 + **已审核的踩坑点**。

**问题是什么**

结构化调用关系导出成 JSON 极其冗长。做 2 跳扩展时一个种子能带出十几个邻居节点，
每个节点的函数体动辄几百行 —— 8k 上下文窗口瞬间爆掉。
于是你被迫要么只扩 1 跳（信息不够），要么截断（截到哪算哪，不可控）。

**这就是"扩得更远"和"塞得进去"的矛盾。摘要头把它变成了可以同时成立的两件事。**

**量化结果（这是简历上最硬的一行）**

| 配置 | Recall@10 | 平均上下文 token |
|---|---|---|
| 不做图扩展 | 59.0% | 3,168 |
| 图扩展，取函数体 | 62.7% | 4,885 |
| **图扩展，取摘要头** ★ | **72.3%** | **4,146** |

**两个指标同向改善**：召回涨 9.6 个点，同时上下文降 15%。
不是常见的"用成本换效果"，而是压缩掉的那部分本来就是噪声 ——
函数体里大量的错误处理、日志、变量声明对"理解调用关系"没有贡献，反而稀释了信号。

**成本设计**：规则版对全量函数生成（免费、秒级，靠注释首行 + 函数名分词）；
`--llm` 只对 `fan_in >= 3` 的高价值函数（约占 10~15%）改写 one_liner。
**成本按节点重要性分配，不是无差别全量调用** —— 这条本身也是个可以讲的设计点。

> **追问：200 token 这个数是怎么定的？**
> 从预算倒推。8k 上下文按 40/25/20/15 分配给 源码/摘要头/经验/Wiki，
> 摘要头这一档是 2k token，2 跳扩展典型带出 10~24 个节点，2000/10 ≈ 200。
> 定长是硬约束：超了就按 pitfalls → key_types → headers → callers → callees 的顺序逐项裁剪，
> 有断言测试 `test_summary_head_token_budget` 守着。实测平均 34.8 token，最大 155。

> **追问：怎么证明摘要头没丢关键信息？**
> 这正是消融表最后两行的意义 —— 如果丢了关键信息，Recall 应该下降。实际是升的。
> 另有测试 `test_graph_expand_returns_heads_not_bodies` 断言摘要头总量小于对应函数体的 1/3。

## ADR-5 为什么用 RRF 融合，而不是加权分数相加

**决策**：`score(d) = Σ wᵢ / (60 + rankᵢ(d))`

**为什么不是 `α·BM25 + β·cosine`**

1. **量纲不同**。BM25 是无界正分（可能 3.2 也可能 47），cosine 是 [-1, 1]。直接相加等于让 BM25 说了算。
2. **分布不同且随查询漂移**。同一个 BM25 分数在不同查询下的"好坏"完全不同，归一化本身就是个难题
   （min-max 会被单个异常值毁掉，z-score 假设了正态分布）。
3. **要调参**。α、β 得针对语料调，换个仓库就得重调，而我没有足够的标注数据支撑调参。

**RRF 只用排名**，天然无量纲、免调参、对异常分数鲁棒。k=60 是文献里的常用默认值，作用是
压平头部差异，避免某一路的第一名过度主导。

**代价**：丢掉了分数的绝对强度信息 —— 一个 BM25 分 47 的强匹配和分 3.2 的弱匹配，
只要排名相同，RRF 就一视同仁。在召回质量差异悬殊时这是缺点。

> **追问：那 symbol 模式的 1.5 倍权重是怎么回事？不是说免调参吗？**
> 那是**通道级**权重，不是分数级。查询里出现 C 标识符或文件名时，
> 符号精确召回这一路整体加权 1.5。只有一个超参，且语义清晰（"用户明确写了符号名，就更信精确匹配"），
> 不是对分数分布的拟合。

<a id="adr-6"></a>
## ADR-6 为什么保留 BM25，而不是纯向量检索

**决策**：符号精确 + BM25 + 向量，三路并行。

**为什么向量单独不够**

C 代码检索有一个向量模型的死穴：**符号名的字面精确性**。
`cJSON_Delete` 和 `cJSON_DeleteItemFromArray`、`mbedtls_ssl_read` 和 `mbedtls_ssl_read_record`，
语义嵌入几乎重合，但它们是**完全不同的东西**，改错一个就是线上事故。
向量检索的"语义相近"在这里恰恰是有害的。

反过来，"输出缓冲区不够时怎么扩容"这种自然语言问题，BM25 完全没辙 ——
代码里那个函数叫 `ensure`，一个字都对不上。

**所以是互补关系，不是替代关系。** 消融表里向量贡献了 57.3% → 59.0%。

> ⚠️ **一个诚实的负面结果（讲这个会加分）**
>
> 消融表第二行显示：BM25 加上符号精确召回后，Recall 从 57.5% **降到** 57.3%，基本没变。
>
> 原因我查了：FTS5 我配的是 `tokenize="unicode61 tokenchars '_'"`，
> 这让整个 `cJSON_Delete` 被当作一个完整 token 索引，**BM25 本身就已经做到了标识符精确匹配**，
> 符号通道是重复劳动。
>
> 那它什么时候有价值？**同名符号消歧**的场景 —— 多个文件里有同名 static 函数、
> 或者跨模块重名时，符号通道能靠 USR 和 `is_definition` 排序做精确定位，BM25 做不到。
> cJSON 这个语料太干净，没有这种情况，所以测不出收益。
>
> 我没有因为"数字不好看"就把这一行从表里删掉。**一个测出来没用的模块，
> 知道它在什么条件下才有用，比假装它一直有用更有价值。**

<a id="adr-7"></a>
## ADR-7 为什么经验库要人工审核，而不是全自动

**决策**：LLM 抽取的经验条目一律 `status='pending'`，**审核前在检索中完全不可见**。

**为什么不全自动（"这不是拖慢效率吗"）**

因为经验库和代码事实的**错误代价不对称**。

代码事实错了，下次解析会覆盖掉。经验错了，它会被检索出来、被人信、被写进新代码，
然后**成为下一条经验的输入**。这是一个正反馈回路 —— 错误经验会自我放大。
一个混入错误经验的知识库，比没有知识库更糟，因为它带着"团队沉淀"的权威感。

LLM 从会话里抽经验时，最容易犯的错误恰恰是**把"当时以为的原因"当成根因写下来**
（会话里前 80% 都在试错，只有最后才转折）。这种错误人一眼能看出，模型看不出。

**实现上怎么保证闸门真的生效**

不是靠"记得过滤"，而是靠数据层：`chunk.visible=0` 的行**根本不进 FTS5 索引**。
就算上层代码写错了，也检索不到。审核通过时才调 `refresh_visibility()` 重建索引。

三个测试守着这条：

```
test_pending_experience_not_retrievable       审核前 B 级命中必须为 0
test_approved_experience_becomes_retrievable  审核后立即可检索
test_cannot_create_approved_directly          不能绕过审核直接插 approved
```

> **追问：审核成本很高怎么办？**
> 承认，这是当前最大的运营成本。缓解方向：① 抽取时输出 `confidence` 字段，
> high 的走快速批准、low 的重点看；② 按关联符号的扇入排序，先审高价值的；
> ③ 批量审同一来源的条目。但**闸门本身不能取消**，只能降低单条成本。

> **追问：`dead_ends`（无效尝试）为什么要单独抽？**
> 因为这是文档里永远不会写的东西。文档写"应该怎么做"，
> `dead_ends` 记录"别人已经试过且不 work 的路"。避免重复踩坑的价值主要来自这一项。

<a id="adr-8"></a>
## ADR-8 为什么做证据分级和拒答

**决策**：

| 级别 | 来源 | 能否作为结论依据 |
|---|---|---|
| A | 编译器确认的代码事实 | 是 |
| B | 人工审核通过的经验 | 是 |
| C | LLM 生成的 Wiki | 仅背景，需标注 |
| D | candidate 关系、未审核内容 | **不进上下文** |

上下文中 A/B 级为 0 时 → **拒答**，只给排查线索。

**为什么不让模型"尽力回答"**

私域代码问答里，**一个自信的错误答案比"我不知道"贵得多**。
用户拿着幻觉出来的函数名去改代码，浪费的是半天；而"证据不足"最多浪费三十秒。

更关键的是**信任的不可逆性**：工具答错一次，人就会开始验证每一个答案，
那这个工具就失去了存在意义 —— 反正都要验证，不如直接看代码。

**分级而不是二值**，是因为 Wiki（C 级）确实有用 —— 它能提供背景和导航，
但它是模型生成的，不能当事实引用。所以让它进上下文但不算"结论依据"。

生成侧强制每个结论句带 `[A1]`/`[B2]` 编号，后端做正则校验。

<a id="adr-9"></a>
## ADR-9 为什么预生成 Wiki，而不是每次现场 RAG

**决策**：离线自底向上生成三层 Wiki（file → module → repo），检索时作为 C 级证据。

这是 Karpathy 的 LLM-Wiki 模式：**知识编译一次并持续维护，而不是每次查询现场重新推导**。

**为什么**

1. **成本**。"这个模块整体是干什么的"这类问题，现场 RAG 每次都要召回几十个函数让模型现读现总结。
   预生成是一次成本、多次复用。
2. **一致性**。同一个问题问两次得到两个不同答案，是知识库的致命伤。预生成的 Wiki 是稳定的。
3. **可审计**。每个 Wiki 页的 frontmatter 里有 `sources[]`，能追溯到具体的代码节点，
   现场生成的答案追溯不了。

**工程上的难点是长任务的稳定性**：生成上百个页面要跑很久，中途崩了不能从头再来。
所以有 `gen_task` 表做断点续写、`input_hash` 做变更失效（输入没变就跳过）、
章节完整性校验（缺必需章节就重试，重试 3 次标 `failed` 但**不阻塞整批**）。

> **追问：代码变了 Wiki 不就过期了吗？**
> 靠 `input_hash` 检测。某个文件的函数摘要头变了 → 该文件的 Wiki 页 `input_hash` 对不上 → 标记 stale 并重生成 → 其上层的 module 页也跟着失效。这是自底向上结构带来的好处：失效能沿着层级正确传播。

<a id="adr-10"></a>
## ADR-10 为什么坚持"无 LLM / 无向量也能跑"

**决策**：`--no-llm --no-vector` 下全流程必须完整跑通，`ask` 返回带引用的证据包。

**为什么这是个设计约束而不是可选项**

1. **可验证性**。任何人 clone 下来，不配 API key、不下模型，`pip install -e . && pytest` 就能验证
   系统是真的能跑 —— 对一个求职项目来说，这比多两个功能重要得多。
2. **强制分层**。这条约束逼着我把"确定性程序"和"模型能力"彻底分开。
   如果允许某个环节离了 LLM 就跑不了，说明那个环节的边界没划清楚。
3. **可调试**。出问题时能先关掉所有不确定因素，确认确定性部分是对的。

实现上：`get_client()` 无 key 返回 `None`，摘要头有规则版，Wiki 有模板版，
向量有 `NullEmbedder`（返回空召回，系统退化为 BM25+图）。

> **追问：那 tfidf 那个 embedder 是什么？**
> 一个不需要下载模型的本地降级实现（TF-IDF + SVD 降维）。
> 它的语义能力当然远不如 BGE 这类真正的嵌入模型，但它让**向量通道在完全离线的环境下可测**，
> 消融表里那一行才有数字。生产上应该换成 `--embedder BAAI/bge-small-zh-v1.5`。
> 我在 EVAL.md 里写明了这一点，没有拿 tfidf 的数字冒充真实嵌入模型的效果。

<a id="adr-11"></a>
## ADR-11 增量解析：为什么指纹要算依赖闭包，为什么边要引用计数

**决策**：默认增量。TU 指纹 = 源文件内容 + 该 TU 依赖的仓库内头文件内容 + 编译参数哈希。
边与 TU 用关联表 `edge_source` 建多对多关系，撤销时按引用计数回收。

**2026-08-31 重跑**（lwIP，124 个 TU）：全量 35.7s → 无变更 0.06s。
本轮未重跑单个 `.c` / `.h` 修改基准，旧环境耗时不再作为当前公开主张。

**难点不在"跳过没改的文件"，在三个地方：**

**① 指纹不能只算 .c 自己。** 改 `netif.h` 会波及所有 include 它的 TU。
所以指纹必须覆盖**依赖闭包**。这里有个先有鸡还是先有蛋的问题 ——
闭包要靠解析结果才知道，所以在首次全量解析时把它存进 `tu_state.deps`。
实测改 `lwip/udp.h` 正确失效了 23 个 TU，改 `netif.h` 失效 67 个。

**② 边必须能被精确撤销。** 节点用 `INSERT OR REPLACE` 覆盖就行，
但边是"某个 TU 观察到的事实"。TU 重解析后，它上次贡献的边必须先撤销 ——
否则**删掉的函数调用会永远留在图里**，影响分析给出幽灵依赖。
这类错误完全静默：不报错、不崩溃，只是悄悄给出错误答案。
所以有测试 `test_removed_call_disappears_from_graph` 专门守。

**③ 同一条边会被多个 TU 观察到。** 头文件里的 `static inline` 函数调用，
每个 include 它的 TU 都会看到一次。按 TU 粗暴删除会误删别人还需要的边。

> ⚠️ **我在这里走了一次弯路，值得讲**
>
> 第一版的做法是把 `tu` 直接加进 `edge` 的唯一键：`UNIQUE(src,dst,kind,confidence,tu)`。
> 逻辑上是对的 —— 每个 TU 存自己那份，按 tu 删除互不干扰。
>
> 但 lwIP 上一跑，**确定边从 11,471 膨胀到 174,071，15 倍**。
> 更糟的不是存储，是**统计口径失真**：README 上"11,471 条确定调用关系"这个数字，
> 会变成"174,071 条" —— 一个听起来更厉害但完全是假的数字。
>
> 改成 `edge` 存逻辑边（唯一键不含 tu）+ `edge_source(edge_id, tu)` 关联表，
> 撤销时先删关联记录，再删"没有任何 TU 再引用"的边。这就是引用计数回收。
> 边数回到 11,753，关联记录 175,945 —— 两个数字各自表达正确的语义。
>
> **教训**：把"来源"塞进实体的唯一键，是把多对多关系硬压成一对多。
> 症状往往先表现为计数异常，而计数异常最危险的地方在于 —— 它会让你的简历数字变成假的。

**最强的正确性判据**：`test_edge_count_matches_full_rebuild` ——
增量跑完的图必须和全量重建**逐边一致**。任何漏删、多删、漏加都会让两边对不上。

<a id="adr-12"></a>
## ADR-12 语料选择：为什么换掉 cJSON

**决策**：主语料从 cJSON 换成 lwIP（135k 行 TCP/IP 协议栈）。

**理由很直接：cJSON 不能证明 D1。**

D1 的前提是"C 工程里函数指针密集，所以必须区分事实与推断"。
但 cJSON 头文件里函数指针声明数是 **0**，实测 fn_pointer 边只有 6 条。
**用它验证等于拿反例证明论点** —— 面试官只要一问"你说函数指针是主要问题，
可你的数据里几乎没有函数指针"，整条论证就塌了。

lwIP 是回调驱动的协议栈：头文件里 127 处函数指针声明，
candidate 里函数指针 + 取地址占 250/282。这才是这个设计要解决的场景。

**mbedtls 保留作对照**，因为它揭示了另一件事：它的 candidate 有 369/380 是 `unresolved`，
成因是条件编译宏，和 lwIP 的分布完全不同。
说明 **candidate 占比反映的是代码风格，不能横向比较** ——
不能说"占比高的项目更需要这个工具"。

<a id="adr-13"></a>
## ADR-13 那个伪装成小毛病的解析缺陷

> ⚠️ 这个坑最值得讲，因为它教的是**怎么读指标**。

lwIP 首次解析时，统计显示"编译诊断错误 124"，而 TU 总数正好也是 124。
**每个文件恰好 1 个错误** —— 这种整齐的数字看起来像无害的小毛病。

实际是：`'stddef.h' file not found`。
libclang 作为**库**被调用时，拿不到 clang 驱动程序才知道的 resource-dir，
于是所有 `#include <stdio.h>` 的链条从第一环就断了。

**症状的迷惑性在于它不会让解析失败**：AST 照样产出，函数照样抽到，
只是标准库相关的类型信息缺失，**能 resolve 的调用变少 —— certain 边被系统性少算**。

补上 builtin 头目录后：诊断错误 124 → 5，certain 边多认出 112 条，
unresolved 类 candidate 从 169 降到 58。

**探测链**做了三级降级：pip wheel 自带 → 系统 LLVM → **GCC 的 include 目录**。
最后一级是实用兜底：这些 freestanding 头（stddef.h / stdarg.h）是编译器无关的，
用 GCC 的喂给 clang 完全可行。这个项目所在的环境里 pip 装的 libclang wheel 就不带头文件，
只能靠这一级救回来。

**教训**：一个"每个文件都有、但只有一个"的错误，比"少数文件有很多错误"更可疑 ——
前者说明是**系统性的环境问题**，后者才是个别代码问题。
指标要看分布，不能只看总数。

<a id="adr-14"></a>
## ADR-14 重排：一次从负收益改到正收益的过程

> ⚠️ 这条建议重点讲。**它的价值不在最终 +0.6pt，在中间那两次失败和根因分析。**

**背景**：主流检索链路是 召回 → 融合 → **重排** → 生成。本项目原来缺重排这一环。
症状很典型：Recall@10 有 68.1%，但 MRR 只有 0.453 ——
**该找的都找到了，只是没排在前面**，这正是重排要解决的。

### 第一版：加上去，指标掉了

一律重排，Recall **68.1% → 62.7%**，MRR 也降。

查具体例子：问 `cJSON_Delete 这个函数做什么`，重排把
`cJSON_DeleteItemFromObject` 顶到了真实调用者前面 —— 因为它前缀匹配。

**根因**：我给 `prefix_symbol` 设了正权重（+0.8）。
但前缀匹配恰恰说明**这是另一个符号** ——
等于把这个项目本来要解决的"同名符号混淆"又引了回来。

### 第二版：改成负权重，还是不如基线

`prefix_symbol` 改为 −0.5，融合分权重从 3.0 提到 6.0
（内容特征是**打破平局**用的，不该推翻召回排序）。

结果 62.7% → **63.9%**，方向对了，但仍低于 68.1% 的基线。

**这时我停止了调权重** —— 继续调就是往评测集上过拟合，
拿到的数字不可信，面试也讲不出所以然。

### 第三版：诊断，发现是"该不该重排"的问题

逐题对比，发现变差的 11 题**全部**是结构性查询
（"改 X 会波及谁"、"X 出问题会间接影响哪些上层函数"），候选集 35~44 条。

机制想通了：

> 问"改 X 会波及谁"，正确答案是调用图上距离较远、
> **但内容上和 X 完全不像**的函数 —— 它们只是可达。
> 而内容特征（精确同名、词覆盖率、是否定义）会把种子函数自己
> 和它的近邻顶上去，把真正的 2 跳答案挤出前十。
>
> **内容相似度在结构性查询上是错误的排序信号。**
> 正确的信号是图距离，而图距离已经编码在融合分里（decay^hop）。

所以正确的做法不是调权重，是**按查询意图决定要不要重排**：
结构性查询（谁调用/影响/波及/调用链）直接跳过内容重排。

结果：**68.1% → 68.7%，MRR 0.453 → 0.464**。

### 为什么用特征线性打分，不用 cross-encoder

留了 cross-encoder 接口，但默认是手写特征线性加权，三个理由：

1. **零模型依赖**，符合"无 key 无模型也能跑通"的一贯约束
2. **完全可解释** —— 能打出每个特征对最终分数的贡献：
   `+9.744 | fusion=+3.00 exact_symbol=+2.50 hop_decay=+1.00 is_definition=+1.00 ...`
   排错时你知道为什么某条排上来了，黑盒模型给不了这个
3. 代码检索的强信号是**结构性**的（是不是定义、是不是精确同名、扇入多少），
   人工就能写对，不需要模型去学

### 必须承认的局限

**这是启发式重排，不是 learning-to-rank。权重是按先验拍的，不是训出来的。**
要训需要带相关性标注的数据，本项目没有。

被问"权重怎么定的"，答案就是上面这句，**不要说成"调参得到的"** ——
调参意味着在测试集上优化，那正是我第二版停下来的原因。

### 守住这些结论的测试

```
test_structural_queries_skip_rerank    结构性查询必须跳过重排
test_prefix_match_is_penalized         前缀匹配权重必须为负
test_fusion_weight_dominates           融合权重必须显著大于内容特征
test_rerank_is_explainable             每条结果必须能给出特征分解
test_tags_resync_after_rerank          重排后引用编号必须重新排
```

最后一条防的是静默错误：citations 重排了但上下文正文里的 `[A1]` 还是旧编号，
模型看到的和用户看到的对不上。

## 项目局限

**主动说，别等着被问出来。** 承认局限比掩盖局限得分高得多。

1. **增量只到 C 文件粒度。** 宏定义变更导致的跨 TU 语义变化没做精确追踪，只能靠头文件哈希兜底。
2. **评测集规模偏小。** 59 题，分五类后每类 10 题左右，置信区间很宽。
   而且只评了检索没评生成质量 —— 后者需要人工打分，成本太高。
3. **`unresolved` 类 candidate 占比过高。** mbedtls 上 369/380，基本都是条件编译宏导致的。
   应该进一步细分（宏展开 / 声明缺失 / 解析错误），目前混在一起。
4. **向量通道用的是 TF-IDF+SVD 降级实现**，不是真正的语义嵌入模型，消融表里那一行的数字偏保守。
5. **人工审核成本高**，且没有做审核协作、冲突处理、知识失效检测。
6. **单用户、无权限、无审计**，离企业级还差一整层。
7. **mbedtls 语料有 84 个编译诊断错误**（缺 tf-psa-crypto 子模块），受影响部分解析不完整。

## 一分钟自述（背下来）

> 我做了一个面向大型 C 工程的 AI 知识库。背景是十万行级的代码仓，
> 传统靠 grep 找不动，直接丢给大模型又会上下文不足、同名符号混淆、答案没法追溯。
>
> 系统分两条链：离线用 libclang 把代码编译成知识图谱，在线用四路混合检索回答问题。
>
> 三个我自己比较满意的设计。
> 第一是**把编译器确认的调用关系和词法推断的分开**，后者不参与影响分析 ——
> 因为一个会给出错误回归范围的工具，被发现一次就没人用了。
> 第二是**定长检索摘要头**，把每个函数的调用上下文压到 200 token 以内，
> 让图多跳扩展和上下文预算这两件事能同时成立，实测召回涨 9.6 个点、上下文反而降 15%。
> 第三是**人工审核硬闸门**，LLM 抽的经验审核前检索命中率为 0，有测试保证 ——
> 因为错误经验会自我放大，比没有经验库更糟。
>
> 在 lwIP 58 题和 cJSON 59 题固定集上做六组消融；完整方案 Recall@10 分别为 64.6%→76.7% 与 56.8%→68.7%，并单独报告 MRR 及循环性边界。
> 过程中踩的最深的坑是……（接 ADR-2 那两个 bug）
