# CodeAtlas 面试表达

## 一句话定位

CodeAtlas 是一个面向复杂 C 工程的可信 AI 研发辅助原型：先把源码变成可验证的工程知识，再让 Agent 按“先理解、后核验”的方式使用它，最后把人工确认的排障经验变成会随代码版本失效的知识资产。

## 60 秒讲法

我当时想解决的不是“再做一个代码聊天框”，而是三个更具体的问题：大模型看到的调用关系是不是真的，历史经验会不会因为代码升级而过期，以及回答错了能不能追到证据。我的做法是用 compile database 和 libclang 建事实层，把可确认关系标为 certain，函数指针等不确定关系只当 candidate；再生成文件、模块、仓库三级 Wiki，让概念题先读工程文档，必要时再回源码。Agent 只有 6 个只读工具，最多调用 6 次，所有回答都绑定当前 commit、USR 和源码范围。会话经验要经过候选确认、源码锚定、QA 和人工审核才能进入检索，定义变化后会自动 stale。最后我在固定版本的 cJSON 和 lwIP 上做了 40 道开发回归题和真实维护场景；两张公开复现实验卡已经人工确认并进入 B 级检索，但旧 40 题仍冻结在早期示例卡身份，因此结果如实保留为 30/40，不事后改 gold。真实模型的 510 个答案试次已经采集，但评分模型没有通过资格校准，所以我不报理解收益。

## STAR（3 分钟）

### S — Situation

复杂 C 工程里，grep 能找到字符串，却不能证明跨文件调用；普通代码 RAG 又容易把相似片段、同名符号或旧版本内容当成事实。研发会话里确实有很多有价值的排障经验，但未经审核直接入库，会把错误尝试和过期结论一起放大。

### T — Task

我的目标是验证一条完整但边界清楚的 AI 应用链路：代码事实能重建，Agent 行为可约束，经验能够人工治理，代码变化会触发知识失效，而且没有 API Key 仍能演示和评测。

### A — Action

1. 我从 `compile_commands.json` 和 libclang 入手，保存 USR、定义范围、定义哈希、构建配置哈希，以及 calls/includes/contains/type_use/field_access/global_ref；只有 certain 调用进入影响分析。
2. 我把 Wiki 做成文件、模块、仓库三级。所有 C/H 文件都有页面，零函数头文件也记录类型、宏和 include；模块调用严格限定作用域，构建后检查所有链接和源码回链。显式分支与错误返回只作为有范围引用的背景，不冒充完整控制流分析。
3. 检索用符号、BM25、local-hash 向量和 certain 图扩展。Wiki 命中后可以沿已校验源码锚点回查 A 级定义；每条证据都携带 repository、revision、USR、文件范围和状态，没有 A/B 证据就在模型前拒答。
4. 我把 Agent 分成 discover、understand、verify。概念/功能/排障题强制先读 Wiki，定位/调用链/影响题直接走结构化工具；`code_read` 只能读当前仓库 C/H 且最多 300 行，整个运行最多 6 次工具调用。
5. 会话先经过公开来源、许可证、复现输入、验证步骤和敏感信息门禁，再设置沉淀目标并生成候选。候选要由人 accept/edit/correct/skip；卡片批准还要有精确主锚点、关系类型和一条通过的 QA。
6. 我用不可变知识快照隔离构建与查询，一次 Agent 固定一个版本。卡片内容保存在 Markdown，发布日志决定是否提交；审核绑定内容、依赖、实验和 QA 的哈希。中断后可恢复，回滚旧源码不会复活已撤销卡。目前依赖采用全实体保守重验证，接受额外复审成本，不宣称能判定语义等价。
7. 评测上，我把 117 道结构回归题、40 道人工任务、6 个安全闭环和可选真实模型 A/B/C 分开，避免拿同源自动题证明自然语言效果。

### R — Result

- cJSON 28 个编译单元、377 个函数定义，生成 34/3/1 个文件/模块/仓库 Wiki；lwIP 124 个编译单元、1167 个函数定义，生成 266/18/1 个 Wiki。两者严重编译诊断均为 0，页面与本地链接完整率 100%。
- 10 道代码检索题上，cJSON 完整方案 Recall@10 为 100%，BM25 为 90%，提升 10pt；lwIP 为 100% 对 80%，提升 20pt。两者 MRR 都上升，certain 影响 F1 都是 1.0，拒答都是 100%。
- 六个闭环场景中，Wiki-first、工具合法、A 级锚点、审核/QA/失效/替代、Markdown 重建和拒答门禁均为 100%，原始会话入索引为 0。
- 40 道旧开发回归目前是 30/40：20 道代码检索、4 道影响和 6 道拒答全部通过，真实检索失败为 0；10 道经验题仍显示审核阻塞，是因为冻结清单绑定早期示例卡及不同题义，不是因为当前没有 B 卡。两张正式卡已由用户确认，均通过 QA、精确锚定、版本发布和 Top-10 检索验证。旧题不在看过结果后改 gold，另以与卡片内容一致的验收记录证明发布状态。
- 真实 Luna 已完成 24 个开发冒烟和 486 个正式答案试次；新版校准先把 point、禁止断言、语义引用与最终判定拆开，两名 source reviewer 核验了 gold，但 Luna judge 仅命中 45/66 和 50/66 个 point，未过门禁。系统因此没有启动正式评分，也没有为了出数字而降低阈值；当前仍不声称 CodeAtlas 已提升模型正确率。

以上 40 题已经用于开发调试，属于回归结果，不是模型理解效果。知识层证明已拆成独立留出候选、同源会话材料和维护变异三组实验；不能把锚点命中或 Wiki-first 顺序当成理解分数。原始试次与审核材料保留，三次重复不当作三道独立题。[三类证明协议和可填写话术](design/VALUE-PROOF-PROTOCOL.md)

当前新增的、可以如实说的维护结果是：24 个真实上游变更场景全部在固定 cJSON/lwIP 临时副本中运行并通过执行完整性校验；四类故障各两例，分别触发编译失败、产物篡改、真实发布日志中断恢复和治理回滚。首轮全仓指纹会误伤所有无关变化；改为审核声明的消费依赖后，8 个有效变化全部重验证，8 个无关变化全部保留，决策 16/16，漏放和误失效均为 0。本机本次依赖指纹计算约 0.81 秒。仅主锚点基线为 13/16，全部失效基线为 8/16。能说的是“冻结场景上的失效与恢复决策成立”；完整重建、真人复核时间和摊销收益仍未测。

## 简历写法

**CodeAtlas｜面向复杂 C 工程的可信 AI 研发辅助原型**

- 基于 `libclang + compile_commands.json` 构建版本化代码事实层，抽取 USR、定义哈希、显式分支和调用/类型/字段/全局引用，以 `certain/candidate` 隔离不确定关系；生成全文件覆盖、可增量重建且零断链的三级 Wiki。
- 实现 Wiki-first 渐进 Agent 与 A/B/C 证据链：6 种白名单只读工具、源码范围和路径越界限制、无 A/B 证据前置拒答；cJSON/lwIP 人工检索 Recall@10 相对 BM25 分别提升 10/20pt，MRR 均上升。
- 设计会话知识策划与 Markdown 主源治理：候选确认、精确主锚点、QA、人工审核、`stale/superseded` 和全量重建；固定闭环评测中工具、引用、审核/失效/重建与拒答门禁均为 100%，原始会话入索引为 0。

## 高频追问

### 参考了 LLM Wiki 吗？

参考的是将临时理解编译成持久知识的模式，不是套用一个同名应用。原文是原始资料、Wiki 和约束规则三层；CodeAtlas 的文件/模块/仓库层级是 C 工程内部的组织方式。我额外处理了编译器事实、固定快照、证据等级、人工发布和版本失效。当前仍偏工程摘要，没有把跨函数综合或知识层收益当作已验证能力。[设计来源](design/LLM-WIKI-LINEAGE.md)

### 为什么不是纯 RAG？

RAG 擅长找相似内容，但“谁调用谁”“这个结论属于哪个 commit”需要结构化事实。CodeAtlas 让编译器负责事实、检索负责召回、模型负责规划和表达，最后仍回到当前源码。

### Wiki 会不会也是幻觉？

规则版从结构化事实生成骨架。模型只能重排已有事实块，不能靠配一个真实引用就新增结论；自由叙述单列待复核。比如 cJSON_Delete 是否释放 child 受 reference 标志和 child 是否为空控制，但跳过 child 不等于函数不再释放其他内容。Wiki 仍是 C 级背景，不是完整控制流证明。

### Agent 比检索多了什么？

它会根据问题类型决定先读 Wiki 还是直接走符号/图，再把中间结果带到下一步源码核验。工具权限、顺序、次数和引用都由本地代码校验，模型不能访问 shell、网络、代码写入或审核接口。

### 为什么知识卡要 Markdown 主源？

Markdown 便于 diff 和审阅；但单有旧文件不能证明它仍被批准，所以另有持久化发布日志保存提交状态。索引可以重建，发布日志和 Markdown 要一起备份。

### 目前没完成什么？

主数据库中的 cJSON/lwIP 两张卡已经用户正式批准，但旧 40 题的经验 gold 与当前卡片身份和题义不一致，仍保留 30/40；不能为追求数字事后重写旧 gold。真实模型的 432 个 Wiki 试次和 54 个经验试次已经采集，尚未通过评分资格门禁，因而没有正确率结论。真实上游维护复验在冻结场景上达到 16/16，但没有测完整重建和真人复核成本，不能包装成普遍的“维护高效”。团队服务、IDE/MCP、自动监听和自动改代码明确不在首版范围。

## 三分钟演示

1. 首页看固定 commit、事实规模和全文件 Wiki；
2. 问一个功能题，看 Agent 先 `search → outline → section`，再读源码；
3. 问调用链或影响题，看 certain 图直接路由与 candidate 分栏；
4. 打开会话沉淀页，展示质量门禁、知识角色、候选决策和人工审核记录；
5. 展示已批准的 B 卡如何进入 Top-10，并用真实重解析演示 `stale`；
6. 回首页解释旧回归为何仍是 30/40，以及为什么 510 个真实答案完成后仍因 judge 校准失败而不发布收益数字。
